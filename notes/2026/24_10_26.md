# Playwright (Browser Automation)

Let us not just learn to automate browsers. Let us learn to understand how software behaves, how users interact with applications, and how to verify that the application works correctly.

Imagine a student developing an online insurance application. The login page looks perfect. The APIs are working. The database stores customer information correctly.

But what happens when a user enters an invalid password, clicks Submit twice, refreshes the page, or opens the application on a different browser?

That is where Browser Automation and Playwright become important.

## 1. What is Browser Automation?

Browser automation means using a program to control a web browser and perform actions that a real user would perform.

- Open a website.
- Enter username and password.
- Click buttons and navigate pages.
- Verify messages and results.
- Capture screenshots.
- Execute regression tests automatically.

For example, instead of manually testing a login page 100 times, we write a test script and let the browser execute those steps.

## 2. What is Playwright?

Playwright is an open-source browser automation framework developed by Microsoft. It supports browser automation and end-to-end testing across Chromium, Firefox and WebKit, with language bindings including Python, JavaScript, TypeScript, Java and .NET. Think of Playwright as a virtual tester that interacts with your application through a real browser engine.

## 4. How does it work?

1. *Test script*: The tester writes test instructions using Python with pytest or TypeScript with Playwright Test.
2. *Playwright API*: The script locates elements, enters data, clicks buttons, navigates pages and checks expected results.
3. *Browser engine*: Playwright controls Chromium, Firefox or WebKit to execute browser interactions.
4. *Web application*: The browser renders the UI. User actions may trigger API calls, business logic and database operations.
5. *Assertions*: Playwright verifies the observable outcome, such as a success message, dashboard heading or validation error.

## 6. Mentor's important distinction

- *pytest / Playwright Test*: Runs and organizes test cases.
- *Playwright API*: Provides browser-control and assertion capabilities.
- *Browser engine*: Executes browser behavior and renders the application.
- *Web application*: Contains the frontend, backend, business rules and data.

Remember: Playwright does not directly test every internal database operation by default. It tests the user-visible workflow through the browser; API tests and database-level checks can complement it. Understand the architecture first, write the test second, and automate the workflow third.

## 3. Step 2 — Create your first browser test

Create a folder named `tests` and inside it create a file named `test_browser.spec.js`.

Project structure:

```
transflower-playwright-lab/
│
├── tests/
│   └── test_browser.spec.js
│
├── package.json
└── package-lock.json
```

Write the following JavaScript code.

```

const { test, expect } = require('@playwright/test');

test('Transflower - verify home page', async ({ page }) => {

    // Step 1: Navigate to the website
    await page.goto('https://example.com');

    // Step 2: Verify the page title
    await expect(page).toHaveTitle('Example Domain');

    // Step 3: Find the main heading
    const heading = page.getByRole('heading', { name: 'Example Domain'});

    // Step 4: Verify that the heading is visible
    await expect(heading).toBeVisible();

    // Step 5: Capture a screenshot
    await page.screenshot({path: 'homepage.png'});

});

```

Code explaination:

- `require()` imports the Playwright testing tools.
- `test()` defines an automated test case.
- `async` allows the test to work with asynchronous operations.
- `await` waits for each asynchronous operation to complete.
- `{ page }` is a Playwright fixture that provides an isolated browser page.
- `page.goto()` navigates to the website.
- `getByRole()` locates an element using its accessible role and name.
- `expect()` verifies the expected behavior.
- `toBeVisible()` checks that the heading is visible.
- `screenshot()` saves the page image.

Playwright Test includes browser fixtures and retrying assertions, so you don't need to create and close the browser manually in every test.&#x20;

## 5. Understand the important Playwright concepts

| Concept      | Purpose                                    | JavaScript example              |
| ------------ | ------------------------------------------ | ------------------------------- |
| Browser      | Runs the browser engine                    | Chromium                        |
| Page         | Represents a browser tab                   | `page`                          |
| Locator      | Finds a page element                       | `page.getByRole()`              |
| Action       | Interacts with the UI                      | `locator.click()`               |
| Assertion    | Checks expected behavior                   | `expect(locator).toBeVisible()` |
| Auto-waiting | Waits for supported actions and assertions | Built into Playwright           |
| Screenshot   | Captures application state                 | `page.screenshot()`             |
| Test runner  | Discovers and executes tests               | `npx playwright test`           |


Mentor's advice: Avoid fixed delays such as `time.sleep(5)` as your default synchronization strategy. Prefer Playwright's auto-waiting, locator assertions and explicit conditions.

## 11. Implement the scenarios using Playwright and pytest

**Login Automation using Node.js, JavaScript and Playwright**

Let us perform Playwright Test. These tests cover successful login, invalid password, empty fields, and access to a protected dashboard after logout.

### 1. Project structure

```

│
├── tests/
│   └── test_login.spec.js
│
├── package.json
└── package-lock.json
```

Install Playwright Test if you haven't already:

```
npm init -y

npx playwright install chromium
```

### 2. Converted JavaScript test cases

Create `tests/test_login.spec.js`.

```

const { test, expect } = require('@playwright/test');

const BASE_URL = 'http://localhost:8000';

const VALID_USERNAME = 'valid_student';
const VALID_PASSWORD = 'valid_test_password';

// Test 1: Valid credentials should open the dashboard.
test('valid credentials', async ({ page }) => {
    await page.goto(`${BASE_URL}/login`);

    await page.getByLabel('Username').fill(VALID_USERNAME);
    await page.getByLabel('Password').fill(VALID_PASSWORD);

    await page.getByRole('button', { name: 'Login' }).click();

    await expect(page).toHaveURL(`${BASE_URL}/dashboard`);

    await expect(
        page.getByRole('heading', { name: 'Dashboard' })
    ).toBeVisible();
});


// Test 2: Invalid password should display an error.
test('invalid password', async ({ page }) => {
    await page.goto(`${BASE_URL}/login`);

    await page.getByLabel('Username').fill(VALID_USERNAME);
    await page.getByLabel('Password').fill('wrong_password');

    await page.getByRole('button', { name: 'Login' }).click();

    await expect(page.getByRole('alert'))
        .toContainText('Invalid credentials');

    await expect(page).toHaveURL(`${BASE_URL}/login`);
});


// Test 3: Empty fields should not submit successfully.
test('empty input fields', async ({ page }) => {
    await page.goto(`${BASE_URL}/login`);

    await page.getByRole('button', { name: 'Login' }).click();

    await expect(
        page.getByLabel('Username')
    ).toBeVisible();

    await expect(
        page.getByLabel('Password')
    ).toBeVisible();

    // If the fields use HTML required validation:
    await expect(page.getByLabel('Username'))
        .toHaveAttribute('required', '');

    await expect(page.getByLabel('Password'))
        .toHaveAttribute('required', '');
});


// Test 4: Dashboard access should be denied after logout.
test('protected page after logout', async ({ page }) => {
    // Login using the application's real login flow.
    await page.goto(`${BASE_URL}/login`);

    await page.getByLabel('Username').fill(VALID_USERNAME);
    await page.getByLabel('Password').fill(VALID_PASSWORD);

    await page.getByRole('button', { name: 'Login' }).click();

    await expect(page).toHaveURL(`${BASE_URL}/dashboard`);

    // Logout.
    await page.getByRole('button', { name: 'Logout' }).click();

    // Attempt to access the protected page directly.
    await page.goto(`${BASE_URL}/dashboard`);

    await expect(page).toHaveURL(`${BASE_URL}/login`);
});

```

### 4. Python-to-JavaScript mapping

| Python Playwright                          | JavaScript Playwright                                    |
| ------------------------------------------ | -------------------------------------------------------- |
| `def test_valid_credentials(page: Page):`  | `test('valid credentials', async ({ page }) => { ... })` |
| `page.goto(url)`                           | `await page.goto(url)`                                   |
| `page.get_by_label("Username")`            | `page.getByLabel('Username')`                            |
| `.fill("valid_student")`                   | `.fill('valid_student')`                                 |
| `page.get_by_role("button", name="Login")` | `page.getByRole('button', { name: 'Login' })`            |
| `expect(page).to_have_url(url)`            | `await expect(page).toHaveURL(url)`                      |
| `expect(locator).to_be_visible()`          | `await expect(locator).toBeVisible()`                    |
| `expect(locator).to_contain_text(text)`    | `await expect(locator).toContainText(text)`              |

Remember: JavaScript Playwright calls generally use `await` because browser navigation, interactions, and assertions are asynchronous.

### 5. Mentor's testing observations

- Valid login: verifies the happy path.
- Invalid password: verifies error handling.
- Empty fields: checks client-side required-field validation. To test the actual validation message, add an assertion matching your application's HTML or custom error message.
- Logout and protected route: verifies that the application redirects unauthenticated users. A redirect alone does not prove the backend authorization is secure; protected APIs must also enforce authentication.

One important detail: the sample credentials must exist in your test environment, and the application must implement the expected routes, labels, alert message, and logout behavior.

Transflower mentor challenge: Add a fifth test that submits an unknown username and verifies that the application displays an appropriate error without opening the dashboard.

Important: The logout test assumes the dashboard URL redirects to login after logout. Some applications return `401 Unauthorized` or `403 Forbidden` through their APIs instead. Verify both the UI behavior and server-side authorization where appropriate. Use a dedicated test account and avoid committing real credentials.

## 13. Mentor's assessment checklist

- Positive testing — valid credentials.
- Negative testing — invalid credentials.
- Validation testing — empty fields.
- Security testing — logout and protected routes.

- *Unit testing*: Does the function work?
