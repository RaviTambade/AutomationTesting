# Node.js + Supertest

Think like a mentor:

> **“We have written an API. Now how do we prove that the API is actually working?”**

That is where **API testing** comes in.

With Node.js, a very simple and practical combination is:

* **Node.js** → runtime
* **Express.js** → build REST API
* **Jest** → test framework
* **Supertest** → send HTTP requests to our Express application

## 1. First understand the problem

Suppose we have this API:

```text
Client
   |
   | HTTP GET /api/policies
   v
+------------------+
| Express.js API   |
+------------------+
   |
   v
Policies
```

Normally we test it manually using:

```text
Postman
   |
   | GET http://localhost:3000/api/policies
   v
Express API
```

But a professional developer asks:

> “Why should I manually test the same API every time?”

We can write a program that tests the API for us. That program is our **automated test**.

# 2. What is Supertest?

**Supertest is a Node.js library used for testing HTTP APIs.**

It allows us to write:

```javascript
request(app)
    .get('/api/policies')
    .expect(200);
```

Instead of opening Postman manually.

Think of Supertest as:

```text
          Human Tester
               |
             Postman
               |
               v
          HTTP Request
               |
               v
          Express API
```

With Supertest:

```text
          Automated Test
               |
           Supertest
               |
               v
          HTTP Request
               |
               v
          Express API
```

So:

> **Supertest becomes our automated Postman.**

But remember:

> **Supertest sends the request. Jest decides whether the test passes or fails.**

# 3. Simple project

Let's create:

```text
node-api-testing/
│
├── app.js
├── package.json
└── tests/
    └── policy.test.js
```

Install:

```bash
npm init -y
npm install express
npm install --save-dev jest supertest
```

# 4. Create Express API

### `app.js`

```javascript
const express = require("express");

const app = express();

app.use(express.json());

const policies = [
    {
        id: 1,
        name: "Jeevan Labh",
        premium: 15000
    },
    {
        id: 2,
        name: "Jeevan Arogya",
        premium: 12000
    }
];

// GET all policies
app.get("/api/policies", (req, res) => {
    res.status(200).json(policies);
});

// GET policy by id
app.get("/api/policies/:id", (req, res) => {

    const id = Number(req.params.id);

    const policy = policies.find(p => p.id === id);

    if (!policy) {
        return res.status(404).json({
            message: "Policy not found"
        });
    }

    res.status(200).json(policy);
});

module.exports = app;
```

Notice something important.

We **did not write**:

```javascript
app.listen(3000);
```

Why? Because during testing, Supertest can directly work with the Express application.


# 5. Create the test

### `tests/policy.test.js`

```javascript
const request = require("supertest");
const app = require("../app");

describe("Policy API", () => {

    test("GET /api/policies should return all policies", async () => {

        const response = await request(app).get("/api/policies");

        expect(response.statusCode).toBe(200);
        expect(response.body.length).toBe(2);
    });

});
```

Now we have automated our first API test.


# 6. What is happening here?

This line:

```javascript
const response = await request(app)
```

means:

> “Supertest, please work with my Express application.”

Then:

```javascript
.get("/api/policies")
```

means:

> “Send a GET request.”

Conceptually:

```text
Test
 |
 | GET /api/policies
 v
+--------------------+
| Express application|
+--------------------+
 |
 | response
 v
response
```

Then:

```javascript
expect(response.statusCode).toBe(200);
```

means:

> “I expect the API to return HTTP 200.”


# 7. Test the JSON response

We can also check the actual data.

```javascript
test("GET /api/policies should return policies", async () => {

    const response = await request(app)
        .get("/api/policies");

    expect(response.statusCode).toBe(200);

    expect(response.body[0].name)
        .toBe("Jeevan Labh");

});
```

We are testing two things:

```text
HTTP Contract
     +
Data Contract
```

For example:

```text
GET /api/policies

Expected:

Status = 200

Body =
[
   {
      "id": 1,
      "name": "Jeevan Labh",
      "premium": 15000
   }
]
```

# 8. Testing GET by ID

```javascript
test("GET /api/policies/1 should return policy", async () => {

    const response = await request(app)
        .get("/api/policies/1");

    expect(response.statusCode).toBe(200);

    expect(response.body.id).toBe(1);

    expect(response.body.name)
        .toBe("Jeevan Labh");
});
```

# 9. Testing 404

A good tester doesn't test only the happy path. We also test:

```text
What happens if policy doesn't exist?
```

```javascript
test("GET invalid policy should return 404", async () => {

    const response = await request(app)
        .get("/api/policies/999");

    expect(response.statusCode).toBe(404);

    expect(response.body.message)
        .toBe("Policy not found");
});
```

This is very important.

> **Good testing means testing both success and failure scenarios.**

# 10. POST testing

Suppose we add:

```javascript
app.post("/api/policies", (req, res) => {

    const policy = {
        id: policies.length + 1,
        name: req.body.name,
        premium: req.body.premium
    };

    policies.push(policy);

    res.status(201).json(policy);
});
```

Now Supertest can send JSON.

```javascript
test("POST /api/policies should create policy", async () => {

    const newPolicy = {
        name: "Jeevan Suraksha",
        premium: 18000
    };

    const response = await request(app)
        .post("/api/policies")
        .send(newPolicy);

    expect(response.statusCode).toBe(201);

    expect(response.body.name)
        .toBe("Jeevan Suraksha");

});
```

Notice this:

```javascript
.send(newPolicy)
```

Supertest converts this into an HTTP request body. Conceptually:

```text
POST /api/policies

Content-Type: application/json

{
    "name": "Jeevan Suraksha",
    "premium": 18000
}
```

# 11. PUT testing

For example:

```javascript
test("PUT /api/policies/1 should update policy", async () => {

    const updatedPolicy = {
        name: "Jeevan Labh Updated",
        premium: 20000
    };

    const response = await request(app)
        .put("/api/policies/1")
        .send(updatedPolicy);

    expect(response.statusCode).toBe(200);

    expect(response.body.name)
        .toBe("Jeevan Labh Updated");

});
```

# 12. DELETE testing

```javascript
test("DELETE /api/policies/1 should delete policy", async () => {

    const response = await request(app).delete("/api/policies/1");

    expect(response.statusCode).toBe(204);
});
```

> **“I tested your API, and your API passed the expected behavior.”**

# 15. One important architectural lesson

For classroom demos, students often write everything in one file:

```text
app.js
 ├── routes
 ├── business logic
 ├── database
 └── server
```

But gradually we should move toward:

```text
project
│
├── app.js
├── server.js
│
├── routes
│   └── policy.routes.js
│
├── controllers
│   └── policy.controller.js
│
├── services
│   └── policy.service.js
│
├── repositories
│   └── policy.repository.js
│
└── tests
    └── policy.test.js
```

And testing becomes:

```text
                Supertest
                    |
                    v
             HTTP Endpoint
                    |
                    v
              Controller
                    |
                    v
               Service
                    |
                    v
             Repository
                    |
                    v
                Database
```

This is where API testing becomes part of **software engineering**, not just Postman practice.

## 16. Mentor's key message

I would explain it to students this way:

> **Postman is excellent for learning and manually exploring an API.**
>
> **Supertest is excellent when we want the computer to repeatedly test our API.**
>
> **Jest gives us the testing framework and assertions.**
>
> **Express gives us the API.**

So remember:

```text
Node.js
   ↓
Express
   ↓
REST API
   ↓
Supertest
   ↓
HTTP Request
   ↓
API Response
   ↓
Jest
   ↓
PASS / FAIL
```

And the real engineering principle is:

> **“Don't just write code. Write code that can prove itself.”**
