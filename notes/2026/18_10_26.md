## 3. What is browser automation?

Imagine a tester manually opens a website, clicks Login, enters an email address, submits the form, and checks whether the dashboard appears.

Browser automation allows a program to perform those browser interactions.

### Manual testing vs. browser automation

*Manual testing*

A human performs the steps and observes the result.

*Browser automation*

A script performs the steps and checks expected outcomes.

The distinction to remember:

- Browser automation means automating browser interactions.
- Automated browser testing means automating those interactions and verifying that actual results match expected results.

For example, clicking Login is an action. Verifying that the correct student dashboard appears is a test assertion.

## 4. Selenium IDE — learning through record and playback


*Selenium IDE*

Selenium IDE is a browser-based record-and-playback tool. It helps learners capture user interactions and replay them as automated test steps.

The supplied session demonstrates recording a sample e-commerce registration flow and exporting the recorded steps into JavaScript code.

### Record-and-playback workflow

1. Create a test project

2. Enter the website URL

3. Start recording browser actions

4. Replay and inspect test results

5. Export the script and review the code

Classroom example: A tester records a registration workflow, including opening the sign-in page, entering data, and navigating through the form.

The recorded script can then be reviewed and maintained. Recording is a starting point—not proof that the application works correctly.

Mentor's lesson: Do not stop at recording the test. Understand each generated step, locator, assertion, and failure.

## 5. What is Playwright?


*Playwright*

Playwright is an open-source browser automation framework used to automate web applications. With Playwright Test, developers and QA engineers can write, execute, and organize browser tests with assertions, fixtures, and reporting.

It supports Chromium, Firefox, and WebKit browser engines.

### What can Playwright do?

- Open a web application.
- Navigate between pages.
- Locate buttons, links, and input fields.
- Enter data and perform clicks.
- Verify expected page content and application behavior.
- Capture screenshots and execution traces when configured.
- Run repeatable tests across supported browsers.

A simple example:

```
const { test, expect } = require('@playwright/test');

test('student can open the portal', async ({ page }) => {
  await page.goto('https://example.com');

  await expect(page).toHaveTitle(/Example Domain/);
});
```

This test opens a page and verifies its title. Replace the example URL and expected title with the actual application under test.

## 6. Understanding the automation testing layers

A web application contains multiple layers. Each layer needs an appropriate testing approach.

*Layer 1 — Unit testing*

Tests individual functions or components in isolation. In the session, Jest is used as the JavaScript unit-testing example.

*Layer 2 — API testing*

Tests HTTP endpoints, request and response behavior, status codes, and validation. The session introduces Supertest for testing Node.js APIs.

*Layer 3 — Browser / end-to-end testing*

Tests user journeys through the web interface using Playwright.

*Layer 4 — Integration and performance testing*

Integration testing verifies interactions between components. Load testing evaluates behavior under workload and requires appropriate performance-testing tools.

### Example: Login workflow

| Test layer  | What should be verified?                                                             |
| ----------- | ------------------------------------------------------------------------------------ |
| Unit        | Login validation function returns the expected result.                               |
| API         | Login endpoint returns the correct status and response for valid and invalid inputs. |
| Browser     | User enters credentials and sees the correct dashboard or error message.             |
| Integration | UI, authentication API, and data services work together correctly.                   |
| Performance | Login service behaves acceptably under expected concurrent load.                     |

Important: These layers complement one another. A browser test does not replace unit or API testing, and API testing does not prove that the user interface works correctly.

## 7. Practical lab — Transflower Student Portal

The classroom discussion applies Playwright to a realistic Transflower portal scenario.

Objective: Automate student login, dashboard verification, and error handling.

### Test scenarios

| Test case                | Action                                         | Expected result                       |
| ------------------------ | ---------------------------------------------- | ------------------------------------- |
| TC01 — Valid login       | Enter valid credentials and submit             | Student dashboard appears             |
| TC02 — Invalid login     | Enter invalid credentials                      | Appropriate error message appears     |
| TC03 — Empty credentials | Submit without required fields                 | Validation messages appear            |
| TC04 — Assessment access | Log in and open assessment results             | Authorized student sees their results |
| TC05 — Regression        | Repeat critical login workflows after a change | Existing behavior remains correct     |

### Example Playwright test

```
const { test, expect } = require('@playwright/test');

test('invalid login displays an error', async ({ page }) => {
  await page.goto('https://example.com/login');

  await page.getByLabel('Email').fill('invalid@example.com');
  await page.getByLabel('Password').fill('incorrect-password');

  await page.getByRole('button', { name: 'Login' }).click();

  await expect(
    page.getByRole('alert')
  ).toBeVisible();
});
```

This is a teaching example. Replace the URL, labels, button name, and expected error behavior with those actually implemented in the student portal. Do not use real student credentials in shared test scripts.

## 8. From test execution to CI/CD

Automation becomes more valuable when tests are repeatable and run consistently during software delivery.

1. Developer commits code
2. Git branch / pull request
3. CI pipeline builds the application
4. Dependency installation and build validation
5. Run automated tests

*Unit tests → API tests → browser smoke/regression tests*

*Evaluate quality results*

Pass/fail • Test reports • Failure diagnostics

*Deployment and verification*

Release approval rules • Smoke tests • Monitoring

A CI/CD pipeline can execute tests automatically, but a pipeline alone does not guarantee quality. The tests must be meaningful, reliable, and connected to appropriate release criteria.

### What a QA Lead should monitor

- Test pass/fail rate and trends.
- Defect severity and unresolved critical defects.
- Regression coverage for business-critical workflows.
- Flaky tests and repeated test failures.
- Build and deployment validation results.
- Evidence supporting release-readiness decisions.

## 10. AI-assisted test automation

Use AI to help transform or explain existing Selenium WebDriver code into Playwright code.

A productive workflow is:

1. Start with a clear test scenario and acceptance criteria.
2. Ask an AI coding assistant to generate a draft test.
3. Review the generated locators, assertions, waits, and test data.
4. Run the test in the target environment.
5. Investigate failures and correct the underlying issue.
6. Include the verified test in the project and CI pipeline.

AI-generated code must be reviewed. A test that passes because its assertions are weak—or because it reproduces the wrong behavior—is not a successful test.

## 11. Quality mindset

Consider two engineers.

- Engineer A focuses on making the code run.
- Engineer B understands the customer requirement, identifies risks, verifies behavior, and checks whether the implementation satisfies the acceptance criteria.

A strong engineering team needs both implementation skills and an independent quality perspective. Developers should write tests, while QA engineers should understand code and systems deeply enough to challenge incorrect assumptions.

For a QA Lead, quality is not simply the number of test cases executed. It is the confidence that the product meets requirements without exposing customers to unacceptable risk.
