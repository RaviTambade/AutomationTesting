# **3. TypeScript Development Environment**

TypeScript is a superset of JavaScript. It adds static typing, interfaces, compile-time checking and other developer productivity features.

The TypeScript compiler converts TypeScript source code into JavaScript.

## **Development workflow**

```
TypeScript Source Code
       │
       ▼
    tsc Compiler
       │
       ▼
JavaScript Output
       │
       ▼
 Node.js Runtime
       │
       ▼
 Program Execution
```

```
mkdir typescript-learning
cd typescript-learning

npm init -y
npm install typescript --save-dev
```

### **Step 2: Initialize TypeScript configuration**

```
npx tsc --init
```

### **Step 3: Project structure**

```
typescript-learning/
│
├── src/
│   ├── banking.ts
│   ├── employee.ts
│   └── index.ts
│
├── dist/
│
├── package.json

```

The purpose of maintaining separate folders is to distinguish source code from generated output.

- `src` – developer-written TypeScript code.
- `dist` – compiled JavaScript code.
- `tsconfig.json` – compiler configuration.

# **5. Understanding Classes and Objects**

The mentor introduced OOP concepts using a practical banking scenario.

## **Real-world analogy**

Imagine a bank has thousands of customers.

Every customer may have:

- Account number
- Customer name
- Account type
- Balance

Every account may perform operations:

- Deposit
- Withdraw
- Transfer
- Display balance

Instead of writing separate code for every account, we create a common blueprint called a **class**.

```
                SavingAccount
                (Blueprint)
                     │
         ┌───────────┼───────────┐
         ▼           ▼           ▼
      Account 1   Account 2   Account 3
      Balance     Balance     Balance
      ₹10,000     ₹50,000     ₹5,000
```

## **Class vs Object**

| Class              | Object               |
| ------------------ | -------------------- |
| Blueprint          | Real instance        |
| Defines properties | Stores actual values |
| Defines behaviour  | Executes behaviour   |
| Logical definition | Runtime entity       |

# **6. Creating a Class in TypeScript**

```
class SavingAccount {

    accountNumber: number;
    customerName: string;
    balance: number;

    constructor(
        accountNumber: number,
        customerName: string,
        balance: number
    ) {
        this.accountNumber = accountNumber;
        this.customerName = customerName;
        this.balance = balance;
    }

    display(): void {
        console.log("Account Number:", this.accountNumber);
        console.log("Customer:", this.customerName);
        console.log("Balance:", this.balance);
    }
}
```

### **Understanding the class**

```
class SavingAccount
```

Defines a new class.

```
accountNumber: number;
customerName: string;
balance: number;
```

These are the object's properties, representing its state.

```
constructor(...)
```

The constructor initializes an object when it is created.

```
this.balance = balance;
```

The `this` keyword refers to the current object's instance.

```
display(): void
```

A member function represents behaviour.

## **7. Creating Multiple Objects**

```
const acc1 = new SavingAccount(101, "Amit", 10000);

const acc2 = new SavingAccount(102, "Sneha", 50000);

const acc3 = new SavingAccount(103, "Rahul", 25000);

acc1.display();
acc2.display();
acc3.display();
```

### **What happens when we create objects?**

```
new SavingAccount(101, "Amit", 10000);
```

The `new` keyword:

1. Allocates an object.
2. Creates its instance properties.
3. Invokes the constructor.
4. Initializes the object.
5. Returns the object reference.

Each object has independent state.

```
acc1 ──► Account { 101, Amit, 10000 }

acc2 ──► Account { 102, Sneha, 50000 }

acc3 ──► Account { 103, Rahul, 25000 }
```

**Mentor's analogy:** A class is like a bank's account-opening form design. Every customer uses the same form, but each customer's information is different.

# **8. Implementing Banking Behaviour**

Objects should not only store data; they should also operate on that data.

The mentor demonstrated business operations such as deposit, withdrawal and transfer.

## **Deposit operation**

```
deposit(amount: number): boolean {

    if (amount <= 0) {
        return false;
    }

    this.balance = this.balance + amount;

    return true;
}
```

### **Logic**

```
Deposit Amount
      │
      ▼
Is amount > 0?
  │          │
 No          Yes
  │           │
  ▼           ▼
Return      Update Balance
False           │
                ▼
             Return True
```

## **Withdraw operation**

```
withdraw(amount: number): boolean {

    if (amount <= 0) {
        return false;
    }

    if (amount > this.balance) {
        return false;
    }

    this.balance = this.balance - amount;

    return true;
}
```

### **Business rules**

- Withdrawal amount must be positive.
- Account should have sufficient balance.
- Balance must be updated only after validation.
- Transaction status must indicate success or failure.

# **9. Why Boolean Status Flags?**

The mentor introduced Boolean return values to communicate the outcome of an operation.

```
const status = acc1.deposit(5000);

if (status) {
    console.log("Deposit successful");
} else {
    console.log("Deposit failed");
}
```

A method should not merely perform an operation. It should communicate whether the requested operation was successful.

```
Method Call
    │
    ▼
deposit(5000)
    │
    ▼
Business Validation
    │
    ▼
Balance Updated?
    │
    ▼
Boolean Result
    │
 ┌──┴───┐
 ▼      ▼
True   False
 │      │
 ▼      ▼
Success Failure
```

### **Important design discussion**

Boolean status is useful for simple demonstrations.

However, in real banking applications, we need more meaningful transaction responses:

```
type TransactionResult = {
    success: boolean;
    message: string;
    transactionId?: string;
    balance?: number;
};
```

For example:

```
{
    success: false,
    message: "Insufficient balance"
}
```

This is more informative than just `false`.

# **11. Object-Oriented Programming – Four Pillars**

The session began introducing the fundamental concepts of object-oriented programming.

## **Four Pillars of OOP**

**1. Encapsulation**

Protect and organize state and behaviour.

**2. Abstraction**

Expose essential behaviour, hide implementation details.

**3. Inheritance**

Reuse and extend existing class behaviour.

**4. Polymorphism**

Same contract, different implementations.

## **11.1 Encapsulation**

Encapsulation means organizing data and the operations that work on that data within a class, while controlling how the data is accessed and modified.

A banking account should not allow anybody to directly change the balance without business validation.

### **Without proper encapsulation**

```
account.balance = -50000;
```

This creates an invalid account state.

### **With encapsulation**

```
class Account {

    private balance: number;

    constructor(initialBalance: number) {
        this.balance = initialBalance;
    }

    deposit(amount: number): boolean {

        if (amount <= 0) {
            return false;
        }

        this.balance += amount;
        return true;
    }

    getBalance(): number {
        return this.balance;
    }
}
```

Now balance modifications happen through controlled operations.

```
External Application
        │
        ▼
  deposit(amount)
  withdraw(amount)
        │
        ▼
 Business Validation
        │
        ▼
 Protected Balance
```

# **12. Inheritance – Extending Existing Classes**

Imagine a bank supports multiple account types:

- Saving Account
- Current Account
- Salary Account
- Fixed Deposit Account

All accounts have common features:

- Account number
- Customer name
- Balance
- Deposit
- Display

But individual account types may have specialized behaviour.

Instead of duplicating common code, we create a base class.

```
                BankAccount
               /           \
              /             \
     SavingAccount       CurrentAccount
```

## **Base class**

```
class BankAccount {

    accountNumber: number;
    customerName: string;
    balance: number;

    constructor(
        accountNumber: number,
        customerName: string,
        balance: number
    ) {
        this.accountNumber = accountNumber;
        this.customerName = customerName;
        this.balance = balance;
    }

    deposit(amount: number): boolean {

        if (amount <= 0) {
            return false;
        }

        this.balance += amount;
        return true;
    }

    display(): void {
        console.log(this.accountNumber, this.customerName, this.balance);
    }
}
```

## **Derived class**

```
class SavingAccount extends BankAccount {

    calculateInterest(): number {
        return this.balance * 0.04;
    }
}
```

## **Usage**

```
const savingAccount =
    new SavingAccount(101, "Amit", 10000);

savingAccount.deposit(2000);

console.log(savingAccount.calculateInterest());

savingAccount.display();
```

### **What does&#x20;**`extends`**&#x20;mean?**

```
class SavingAccount extends BankAccount
```

The `SavingAccount` inherits members from `BankAccount` and can add its own specialized behaviour.

**Mentor's takeaway:** Inheritance is a mechanism for specialization. It should represent a genuine *is-a* relationship, not simply a way to copy code.

# **13. Interfaces – Contracts in Software Engineering**

The mentor introduced interfaces as contracts that define what a class must provide.

Imagine a company wants to build multiple components.

One component may print a report. Another may serialize data. Another may test the component.

The implementation may differ, but the expected behaviour must follow a standard contract.

## **Real-world analogy**

```
Company Contract
       │
       ▼
 Defines Required Behaviour
       │
       ▼
Implementation by Different Teams
       │
       ▼
Contract Compliance
```

An interface tells us:

> What operations must be available?

A class tells us:

> How those operations are implemented?

# **14. Creating an Interface**

```
interface IPrintable {

    print(): void;
}
```

This interface defines a contract.

Any class that implements `IPrintable` must provide the `print()` method.

## **Implementing the interface**

```
class Report implements IPrintable {

    print(): void {
        console.log("Printing report...");
    }
}
```

Another class can implement the same contract differently.

```
class Invoice implements IPrintable {

    print(): void {
        console.log("Printing invoice...");
    }
}
```

### **Visual representation**

```
               IPrintable
             ┌────────────┐
             │ print()    │
             └─────┬──────┘
                   │
         ┌─────────┴─────────┐
         │                   │
         ▼                   ▼
      Report              Invoice
         │                   │
         ▼                   ▼
 Print Report         Print Invoice
```

Both classes satisfy the same contract, but their implementation is different.

# **15. Interface vs Class**

| Interface                                  | Class                           |
| ------------------------------------------ | ------------------------------- |
| Defines a contract                         | Defines structure and behaviour |
| Primarily compile-time construct           | Can exist at runtime            |
| No concrete method implementation          | Can have implemented methods    |
| Cannot be instantiated                     | Can be instantiated             |
| Implemented using `implements`             | Extended using `extends`        |
| Used for abstraction and structural typing | Used to create objects          |

### **Example**

```
interface IAccount {
    deposit(amount: number): boolean;
    withdraw(amount: number): boolean;
}
```

A class implements the contract:

```
class SavingAccount implements IAccount {

    balance: number = 0;

    deposit(amount: number): boolean {
        if (amount <= 0) {
            return false;
        }

        this.balance += amount;
        return true;
    }

    withdraw(amount: number): boolean {
        if (amount <= 0 || amount > this.balance) {
            return false;
        }

        this.balance -= amount;
        return true;
    }
}
```

# **16. Abstraction – Programming Through Interfaces**

One of the important concepts discussed was exposing an object through an interface rather than exposing its concrete class.

Suppose an application needs to perform account operations.

Instead of depending directly on `SavingAccount`, we depend on the `IAccount` contract.

```
interface IAccount {

    deposit(amount: number): boolean;

    withdraw(amount: number): boolean;

    getBalance(): number;
}
```

The concrete class implements this interface.

```
class SavingAccount implements IAccount {

    private balance: number;

    constructor(initialBalance: number) {
        this.balance = initialBalance;
    }

    deposit(amount: number): boolean {

        if (amount <= 0) {
            return false;
        }

        this.balance += amount;
        return true;
    }

    withdraw(amount: number): boolean {

        if (amount <= 0 || amount > this.balance) {
            return false;
        }

        this.balance -= amount;
        return true;
    }

    getBalance(): number {
        return this.balance;
    }
}
```

## **Expose the object through a contract**

```
const account: IAccount =
    new SavingAccount(10000);

account.deposit(5000);

console.log(account.getBalance());
```

The variable `account` is typed as `IAccount`.

Therefore, the consumer works with the operations exposed by the interface.

```
Consumer
   │
   ▼
IAccount Contract
   │
   ▼
SavingAccount Object
   │
   ▼
Actual Implementation
```

### **Why is this important?**

The consumer does not need to know:

- How balance is stored.
- How transactions are validated.
- How deposit is implemented.
- What internal variables exist.

The consumer only needs to know the available contract.

This reduces dependency on implementation details.

# **17. Multiple Interfaces**

A class can implement multiple interfaces in TypeScript. This allows a class to support different capabilities. For example, an account may be:

- Printable
- Serializable
- Auditable
- Transactable

## **Define multiple contracts**

```
interface IPrintable {
    print(): void;
}

interface ISerializable {
    serialize(): string;
}

interface IAccount {
    deposit(amount: number): boolean;
    getBalance(): number;
}
```

## **Implement multiple interfaces**

```
class SavingAccount
    implements IAccount, IPrintable, ISerializable {

    private balance: number;

    constructor(initialBalance: number) {
        this.balance = initialBalance;
    }

    deposit(amount: number): boolean {

        if (amount <= 0) {
            return false;
        }

        this.balance += amount;
        return true;
    }

    getBalance(): number {
        return this.balance;
    }

    print(): void {
        console.log("Balance:", this.balance);
    }

    serialize(): string {
        return JSON.stringify({
            balance: this.balance
        });
    }
}
```

### **Conceptual diagram**

```
IAccount          IPrintable        ISerializable
    │                  │                  │
    └──────────────────┼──────────────────┘
                       │
                       ▼
                 SavingAccount
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    deposit()       print()       serialize()
```

**Mentor's analogy:** Think of a person fulfilling different roles. The same person may be a teacher, evaluator, mentor and developer. Each role represents a different contract of responsibility. Similarly, one software object can implement multiple interfaces.

# **18. Polymorphism – Same Contract, Different Behaviour**

Polymorphism means that different objects can be used through the same contract, while each object performs its own implementation. Suppose we have different account types.

```
interface IAccount {

    deposit(amount: number): boolean;

    getBalance(): number;
}
```

Two implementations:

```
class SavingAccount implements IAccount {

    private balance: number = 0;

    deposit(amount: number): boolean {

        if (amount <= 0) return false;

        this.balance += amount;
        return true;
    }

    getBalance(): number {
        return this.balance;
    }
}
```

```
class CurrentAccount implements IAccount {

    private balance: number = 0;

    deposit(amount: number): boolean {

        if (amount <= 0) return false;

        this.balance += amount;
        return true;
    }

    getBalance(): number {
        return this.balance;
    }
}
```

## **Polymorphic usage**

```
const accounts: IAccount[] = [
    new SavingAccount(),
    new CurrentAccount()
];

for (const account of accounts) {

    account.deposit(1000);

    console.log(account.getBalance());
}
```

The application uses a common interface:

```
              IAccount
                 │
          ┌──────┴──────┐
          ▼             ▼
   SavingAccount   CurrentAccount
          │             │
          ▼             ▼
   Saving Behaviour  Current Behaviour
```

The caller does not need to know the concrete class of every object.

### **Why polymorphism matters in enterprise applications**

Imagine an application supports:

- MySQL repository
- Oracle repository
- SQL Server repository
- Mock repository for testing

All can implement the same repository contract. The consumer can use the same interface without changing its business logic.

# **19. Interface-Based Design in Automation Testing**

This is especially relevant to TAP learners with automation testing experience. Imagine Playwright tests need to work with different browser implementations.

```
interface IBrowser {

    open(url: string): Promise<void>;

    close(): Promise<void>;
}
```

Implementations:

```
class ChromeBrowser implements IBrowser {

    async open(url: string): Promise<void> {
        console.log("Opening Chrome:", url);
    }

    async close(): Promise<void> {
        console.log("Closing Chrome");
    }
}
```

```
class FirefoxBrowser implements IBrowser {

    async open(url: string): Promise<void> {
        console.log("Opening Firefox:", url);
    }

    async close(): Promise<void> {
        console.log("Closing Firefox");
    }
}
```

Consumer:

```
async function runTest(browser: IBrowser) {

    await browser.open("https://example.com");
    console.log("Running test...");
    await browser.close();
}
```

Usage:

```
const chrome = new ChromeBrowser();
const firefox = new FirefoxBrowser();

runTest(chrome);
runTest(firefox);
```

The test execution logic remains unchanged. Only the implementation supplied to the consumer changes. This is the foundation of:

- Test abstraction
- Reusable automation frameworks
- Dependency injection
- Mocking
- Maintainable test architecture

# **20. TypeScript vs JavaScript – Why Interfaces Matter**

JavaScript is dynamically typed. It does not provide TypeScript-style interfaces as a native runtime construct. TypeScript provides interfaces to help developers define contracts and validate structure during compilation.

```
interface IEmployee {
    id: number;
    name: string;
    department: string;
}
```

The compiler validates whether an object satisfies the interface.

```
const employee: IEmployee = {
    id: 101,
    name: "Amit",
    department: "Testing"
};
```

But TypeScript interfaces are erased during compilation.

### **TypeScript**

```
interface IPrintable {
    print(): void;
}
```

### **Generated JavaScript**

The interface does not generate a corresponding JavaScript runtime object.

This is important to understand:

> TypeScript interfaces help us design, validate and organize code at compile time. They are not runtime entities.

# **21. Modules – Export and Import**

During compilation and project organization, module-related adjustments were also discussed. When a class or function needs to be shared across files, we use `export` and `import`.

### `account.ts`

```
export class SavingAccount {

    balance: number = 0;

    deposit(amount: number): void {
        this.balance += amount;
    }
}
```

### `main.ts`

```
import { SavingAccount } from "./account";

const account = new SavingAccount();

account.deposit(1000);

console.log(account.balance);
```

Compile:

```
npx tsc
```

Run the generated JavaScript using Node.js.

```
node dist/main.js
```

### **Why modules?**

Modules help us:

- Separate responsibilities.
- Reuse code.
- Organize large applications.
- Avoid unnecessary global variables.
- Maintain independent components.

# **25. Mentor's Reflection**

The important learning from this session is not memorizing `class`, `interface`, `extends` or `implements`. The important thing is to understand why we use them. When a developer writes a small script, functions may be sufficient. But as the application grows:

- Data needs protection.
- Behaviour needs organization.
- Components need contracts.
- Implementations need flexibility.
- Code needs reuse.
- Testing needs abstraction.

That is where object-oriented design becomes valuable.

> **A good developer writes code that works. A good software engineer designs code that can evolve.**

We started with a simple banking example. The same thinking can be applied to a testing framework, payment system, employee management application, e-commerce platform or enterprise API.

### **Upcoming topic: Generics**

Why should we write separate functions for integers, strings and employees when the same logic can be reused with different types?

```
function identity<T>(value: T): T {
    return value;
}

const numberResult = identity<number>(100);
const stringResult = identity<string>("Transflower");
const employeeResult = identity<Employee>(employee);
```

Generics will take our understanding of interfaces and reusable components to the next level.
