# Test vs Test Case vs Unit Test vs Testing Framework

> **"Testing is the activity. A Test Case is the specification. A Unit Test is executable code. A Testing Framework is the infrastructure that runs and manages those tests."**

Think of a software application like a **car**.

| Term                  | Simple Meaning                                                    | Car Analogy                             |
| --------------------- | ----------------------------------------------------------------- | --------------------------------------- |
| **Test**              | An activity/check performed to verify behavior                    | Check whether the car starts            |
| **Test Case**         | A documented set of conditions, inputs, steps and expected result | Detailed procedure for checking the car |
| **Unit Test**         | Automated test of a small piece of code                           | Test only the engine-start mechanism    |
| **Testing Framework** | Tools/libraries that help create, execute and report tests        | The garage + testing equipment          |

## 1. What is a **Test**?

A **Test** is an attempt to verify whether a software behavior meets an expected requirement.

For example:

> Requirement: User should be able to log in with valid credentials.

A tester performs a test:

```text
Enter username
Enter password
Click Login
Observe result
```

Expected:

```text
User should be successfully logged in.
```

So:

```text
Requirement
     ↓
   Test
     ↓
Actual Result
     ↓
Compare with Expected Result
     ↓
Pass / Fail
```

### Important point

**Test is the broadest concept.**

Testing can be:

* Manual
* Automated
* Unit testing
* Integration testing
* API testing
* UI testing
* Performance testing
* Security testing
* Regression testing


# 2. What is a **Test Case**?

A **Test Case** is a structured description of **how a particular scenario will be tested**.

It normally contains:

```text
Test Case ID
Test Scenario
Preconditions
Test Data
Steps
Expected Result
Actual Result
Status
```

### Example

**TC_LOGIN_001**

```text
Title:
Login with valid username and password

Precondition:
User is registered

Test Data:
Username = ravi
Password = Pass@123

Steps:
1. Open Login page
2. Enter username
3. Enter password
4. Click Login

Expected Result:
User should be redirected to Dashboard.
```

The test case tells the tester:

> **What should I test and how should I test it?**


# 3. What is a **Unit Test**?

A **Unit Test** is an automated test that verifies a **small, isolated unit of application code**. For example, suppose we have:

```csharp
public class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }
}
```

A unit test could be:

```csharp
[Fact]
public void Add_TwoNumbers_ReturnsSum()
{
    var calculator = new Calculator();

    var result = calculator.Add(10, 20);

    Assert.Equal(30, result);
}
```

Here:

```text
Calculator
    ↓
Add()
    ↓
Unit Test
    ↓
Expected = 30
Actual   = 30
    ↓
PASS
```

The important idea is **isolation**.

We are testing:

```text
Add()
```

rather than testing the entire application.

### Unit test characteristics

Usually:

* Small
* Fast
* Automated
* Repeatable
* Isolated
* Focused on one unit of behavior

# 4. What is a **Testing Framework**?

A **Testing Framework** is a software framework that provides the infrastructure required to **write, execute, organize and report automated tests**.

Examples:

### .NET

* xUnit
* NUnit
* MSTest

### Java

* JUnit
* TestNG

### JavaScript / TypeScript

* Jest
* Mocha
* Vitest

### Python

* pytest
* unittest

For example, in .NET:

```text
Application Code
      ↓
   xUnit
      ↓
 Test Methods
      ↓
 Execute
      ↓
 Assertions
      ↓
 Test Result
      ↓
 Report
```

The framework provides things such as:

```text
[Test]
[Fact]
[Theory]

Assert.Equal()
Assert.True()
Assert.False()
```

and mechanisms for:

* Test discovery
* Test execution
* Assertions
* Setup/teardown
* Fixtures
* Parameterized tests
* Test reporting


# 🔍 The Key Difference

The easiest way to remember it is:

```text
TESTING
   │
   ├── Test
   │     └── What are we checking?
   │
   ├── Test Case
   │     └── How exactly are we going to check it?
   │
   ├── Unit Test
   │     └── Automated test of a small unit of code
   │
   └── Testing Framework
         └── What infrastructure runs our automated tests?
```

# 🧑‍💻 Automation Engineer's Perspective

Suppose you are testing an **Insurance Policy API**.

Requirement:

> Customer should be able to create a policy.

### Test

```text
Verify that a customer can create a policy.
```

### Test Case

```text
TC_POLICY_001

Input:
Customer = C101
Product = Life Protection Plan
Premium = ₹25,000

Steps:
1. Login
2. Select customer
3. Select insurance product
4. Enter policy details
5. Submit

Expected:
Policy should be created successfully.
```

### Automated Test

You convert that test case into executable code:

```csharp
[Fact]
public async Task CreatePolicy_ValidData_ReturnsSuccess()
{
    var response = await policyApi.CreatePolicy(policy);

    Assert.Equal(HttpStatusCode.Created, response.StatusCode);
}
```

Now this is an **automated test**.

If this test is specifically testing one isolated method such as:

```csharp
PolicyService.CalculatePremium()
```

then it can be a **unit test**.

### Testing Framework

Perhaps you use:

```text
xUnit
```

to execute it.

# 🏗️ One Important Distinction

Do not assume:

> **Every automated test is a unit test.**

This is a common beginner mistake.

For example:

```text
Unit Test
    ↓
PolicyService.CalculatePremium()
```

But:

```text
Integration Test
    ↓
Policy API
    ↓
Database
```

And:

```text
API Test
    ↓
HTTP Request
    ↓
Policy API
    ↓
Response
```

And:

```text
UI/E2E Test
    ↓
Browser
    ↓
React Application
    ↓
API
    ↓
Database
```

All of these can be **automated tests**, but they are testing at different levels.

# 🎯 Automation Testing Pyramid

A good Automation Test Engineer should understand the relationship between them:

```text
                    ┌───────────────┐
                    │   E2E / UI    │
                    │   Tests       │
                    └───────▲───────┘
                            │
                    ┌───────┴───────┐
                    │  Integration  │
                    │    Tests      │
                    └───────▲───────┘
                            │
                    ┌───────┴───────┐
                    │   Unit Tests  │
                    └───────────────┘
```

Typically:

```text
Many Unit Tests
       +
Some Integration Tests
       +
Fewer E2E Tests
```

because unit tests are generally faster and more isolated, while end-to-end tests exercise more of the system and tend to be slower and more complex.


# 🧠 Remember This as an Automation Engineer

| Concept               | Answers the question                                                   |
| --------------------- | ---------------------------------------------------------------------- |
| **Test**              | **What are we checking?**                                              |
| **Test Case**         | **How are we checking it?**                                            |
| **Unit Test**         | **What small piece of code are we automatically checking?**            |
| **Testing Framework** | **What tool/infrastructure executes and manages our automated tests?** |

### One-line mentor definition

> **Test is the activity, Test Case is the documented specification, Unit Test is executable verification of a small code unit, and Testing Framework is the infrastructure used to write, execute and manage automated tests.**


For a simple **Node.js + Jest** project using CommonJS (`require` / `module.exports`), use this `package.json`:

```json
{
  "name": "jest-demo",
  "version": "1.0.0",
  "description": "Simple Node.js unit testing project using Jest",
  "main": "calculator.js",
  "scripts": {
    "test": "jest",
    "test:watch": "jest --watch",
    "test:coverage": "jest --coverage"
  },
  "keywords": [
    "nodejs",
    "jest",
    "unit-testing"
  ],
  "author": "Transflower Learning",
  "license": "ISC",
  "devDependencies": {
    "jest": "^30.1.3"
  }
}
```

### Install dependencies

If you are creating the project from scratch:

```bash
npm install
```

Or simply:

```bash
npm install --save-dev jest
```

Then run:

```bash
npm test
```

### Recommended project structure

```text
jest-demo/
│
├── node_modules/
│
├── calculator.js
├── calculator.test.js
├── package.json
└── package-lock.json
```

Your test file can be named:

```text
calculator.test.js
```

or:

```text
calculator.spec.js
```

Jest will automatically discover these test files.

### Useful commands

```bash
npm test
```

Run all tests.

```bash
npm run test:watch
```

Automatically rerun tests when files change.

```bash
npm run test:coverage
```

Generate a test coverage report.

**Classroom rule to remember:**

```text
package.json
     │
     ├── dependencies
     │      └── Runtime libraries
     │
     ├── devDependencies
     │      └── Development/testing tools
     │
     └── scripts
            └── npm test → jest
```

For a **Jest + Express + MySQL** project, the next `package.json` would typically include `express`, `mysql2`, `jest`, and possibly `supertest`.
