## 2. Understanding Application Layers

Ravi Sir:

"Students, when you install Express, you are using a web application framework. On top of that framework, you build your application.

But where should your business logic go? Where should your database-related code go?"

### A typical layered application

Presentation Layer

HTML · CSS · React · Browser

Web API / Controller Layer

Express routes · Request and response handling

BLL — Business Logic Layer

Premium calculation · Claim verification · Customer authentication

DAL — Data Access Layer

Read · Insert · Update · Delete

Persistence Layer

JSON file · Database

### Classroom dialogue

Aditya: Sir, what is BLL?

Ravi Sir: Business Logic Layer. Suppose you are developing an insurance application. Premium calculation, claim verification, and eligibility checks belong to business functionality.

Rutuja: Sir, what is DAL?

Ravi Sir: Data Access Layer. It is responsible for interacting with the data source.

Mentor's explanation:

The business logic layer answers:

* Is this customer eligible?

* What is the premium?

* Can this claim be approved?

The data access layer answers:

* How do we retrieve the policy?

* How do we insert a customer?

* How do we update a claim record?

Separating these responsibilities makes the application easier to understand, test, and maintain.

### Step 3: Create the Express application

Create `server.js`:

JavaScript

```
const express = require("express");

const app = express();

const PORT = 3000;

// Middleware to read JSON request bodies
app.use(express.json());

// Temporary in-memory policy collection
let policies = [
    {
        id: 1,
        name: "Jeevan Labh",
        description: "Life insurance policy",
        maturity: "10 years"
    },
    {
        id: 2,
        name: "Jeevan Arogya",
        description: "Health insurance policy",
        maturity: "5 years"
    }
];

// GET: Retrieve all policies
app.get("/api/policies", (req, res) => {
    res.status(200).json(policies);
});

// GET: Retrieve policy by ID
app.get("/api/policies/:id", (req, res) => {

    const id = Number(req.params.id);

    const policy = policies.find(p => p.id === id);

    if (!policy) {
        return res.status(404).json({
            message: "Policy not found"
        });
    }

    res.status(200).json(policy);
});

// POST: Create a policy
app.post("/api/policies", (req, res) => {

    const { name, description, maturity } = req.body;

    if (!name || !description || !maturity) {
        return res.status(400).json({
            message: "All fields are required"
        });
    }

    const newPolicy = {
        id: policies.length
            ? Math.max(...policies.map(p => p.id)) + 1
            : 1,
        name,
        description,
        maturity
    };

    policies.push(newPolicy);

    res.status(201).json(newPolicy);
});

// PUT: Update a policy
app.put("/api/policies/:id", (req, res) => {

    const id = Number(req.params.id);

    const policy = policies.find(p => p.id === id);

    if (!policy) {
        return res.status(404).json({
            message: "Policy not found"
        });
    }

    const { name, description, maturity } = req.body;

    if (!name || !description || !maturity) {
        return res.status(400).json({
            message: "All fields are required"
        });
    }

    policy.name = name;
    policy.description = description;
    policy.maturity = maturity;

    res.status(200).json(policy);
});

// DELETE: Remove a policy
app.delete("/api/policies/:id", (req, res) => {

    const id = Number(req.params.id);

    const policy = policies.find(p => p.id === id);

    if (!policy) {
        return res.status(404).json({
            message: "Policy not found"
        });
    }

    policies = policies.filter(p => p.id !== id);

    res.status(200).json({
        message: "Policy deleted successfully"
    });
});

// Start the server
app.listen(PORT, () => {
    console.log(`Server running at http://localhost:${PORT}`);
});
```

## 5. Understanding Express Request and Response Objects

Before testing, understand the two important objects received by an Express route handler.

JavaScript

```
app.get("/api/policies/:id", (req, res) => {
    // Request comes through req
    // Response is sent through res
});
```

|
Object

|

Purpose

|

Examples

|
| --- | --- | --- |
|

`req`

|

Contains incoming request information

|

`req.params`, `req.body`, `req.query`

|
|

`res`

|

Used to construct and send the response

|

`res.status()`, `res.json()`

|

### Understanding route parameters

For this endpoint:

http

```
GET /api/policies/23
```

The route:

JavaScript

```
app.get("/api/policies/:id", ...)
```

receives:

JavaScript

```
req.params.id
```

with the value `"23"`.

Because route parameters are strings, we convert the value when we need a numeric ID:

JavaScript

```
const id = Number(req.params.id);
```

### Understanding request body

A client can submit JSON:

JSON

```
{
  "name": "Child Future Plan",
  "description": "Savings-oriented insurance plan",
  "maturity": "15 years"
}
```

Express middleware:

JavaScript

```
app.use(express.json());
```

allows the application to parse JSON request bodies.

The parsed information becomes available through:

JavaScript

```
req.body
```

### Understanding response methods

JavaScript

```
res.status(200).json(policies);
```

This sets the HTTP status code and sends JSON data.

JavaScript

```
res.status(404).json({
    message: "Policy not found"
});
```

This sends a not-found response.

Mentor's note: Students should understand the request-response lifecycle rather than memorizing individual Express methods.

## 7. Important Observation: Where Is Our Data Stored?

Rutuja: Sir, after creating a policy, where is the data stored?

Ravi Sir: Currently, inside our JavaScript array.

Rutuja: What happens if we stop the server and start it again?

Ravi Sir: The newly created policy will be lost because we have not implemented persistent storage.

This is an important architectural limitation.

## In-Memory Data vs Persistent Data

Current implementation

Express API → JavaScript array → Process memory

Future implementation

Express API → Data Access Layer → Database

The current application is suitable for learning HTTP methods and CRUD operations, but it is not yet a persistent production data solution.

### Next architectural improvement

```
TFLInsuranceAPI/
│
├── src/
│   ├── routes/
│   │   └── policyRoutes.js
│   │
│   ├── controllers/
│   │   └── policyController.js
│   │
│   ├── services/
│   │   └── policyService.js
│   │
│   ├── repositories/
│   │   └── policyRepository.js
│   │
│   └── app.js
│
├── server.js
└── package.json
```

This structure introduces separation of responsibilities.

The repository can initially use an array or JSON file, and later be replaced with database operations.

|

What to investigate

|
|

|

|
|

API returns 404

|

|
|

Policy not found

|

|
|

Data disappears after restart

|

Is data stored only in memory?

|
|

`NaN` during ID comparison

|

Has the route parameter been converted to a number?

|

### Debugging mindset

Instead of randomly changing code, ask:

1. What was the expected behavior?

2. What actually happened?

3. What input triggered the issue?

4. Which application layer is responsible?

5. Can I reproduce the issue consistently?

6. What evidence can I provide to the developer?
