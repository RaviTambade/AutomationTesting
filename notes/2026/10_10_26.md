# Transflower Mentor Notes: Secure REST API and JWT Authentication

For Automation Test Engineers | Node.js, REST API, Postman, Jest and Supertest

## 1. Start with a real-world story

Imagine we are developing the TFLInsurance Policy Management System at Transflower.

An insurance company has different users:

- A customer wants to view their own insurance policies.
- An insurance agent wants to access policies associated with their customers.
- An insurance manager wants to approve or reject claims.
- An administrator wants to manage users and roles.

Now imagine that we expose a REST API:

`GET /api/policies`

Anyone who knows this URL might try to access it. Should the server return insurance data to everyone?

Of course not!

As Transflower mentors, we teach students to think beyond writing an API endpoint. We ask:

How do we know who is making the request? What is that user allowed to do? How can an Automation Test Engineer verify that the API is secure?

These questions introduce us to authentication, authorization, JWT tokens, and security testing.

## 2. What is a Secure REST API?

A REST API allows applications to communicate over HTTP using methods such as GET, POST, PUT, PATCH and DELETE.

A secure REST API protects its data and operations by checking the identity, permissions and validity of incoming requests.

Consider these security layers:

Client Application / Postman

Sends HTTP request with headers and data

Authentication

Who are you? Validate identity and token.

Authorization

Are you allowed to perform this operation?

Business Logic → Database

Process the request and return an appropriate response.

For example, an API may require a valid token before returning policy details. It may then check whether the authenticated user owns the requested policy.

Remember these two questions:

- Authentication: Who are you?
- Authorization: What are you allowed to do?

A valid token does not automatically give a user permission to access every resource.

## 3. What is JWT?

JWT stands for JSON Web Token. It is a compact format for carrying claims about a user or another identity between systems.

After a user successfully logs in, the server may issue a JWT. The client sends it with subsequent API requests.

A typical JWT has three parts separated by dots:

`header.payload.signature`

1\. Header

Describes the token type and signing algorithm.

Example: `{"alg":"HS256","typ":"JWT"}`

2\. Payload

Contains claims such as subject, user ID, role, issue time and expiration.

Example: `{"sub":"user-102","role":"Customer","exp":1790000000}`

3\. Signature

Allows the server to verify that the token has not been altered and was signed using the expected key or signing configuration.

Mentor's important lesson: A JWT is normally encoded, not encrypted. Anyone possessing a standard signed JWT can often decode and read its header and payload. Never put passwords, secret keys or other confidential information inside an ordinary JWT payload.

The signature protects integrity; it does not hide the contents.

## 4. How JWT Authentication works — step by step

Let's understand the complete journey of a request in TFLInsurance.

## 1

Login request

The customer submits their username and password.

`POST /api/auth/login`

## 2

Server validates credentials

The server checks the user's credentials against the stored account information. Passwords should be stored using a secure password hash, not plaintext.

## 3

JWT is issued

If authentication succeeds, the server creates and signs a token with an expiration time.

## 4

Client sends the token

Every protected request includes the token in the HTTP Authorization header.

`Authorization: Bearer <access_token>`

## 5

API validates and authorizes

The server verifies the signature, expiration, issuer, audience and other configured requirements, then checks permissions and resource ownership.

Response is returned

If all checks succeed, the API processes the request and returns the appropriate response. Otherwise, it rejects the request.

A JWT-based API typically does not need to look up the user's password on every request. It can validate the signed token. However, revocation, account disabling and permission changes may require additional checks or a short-lived token strategy.

## 5. What does an Automation Test Engineer do?

A developer implements the security mechanism. An Automation Test Engineer verifies that the mechanism behaves correctly under both valid and invalid conditions.

For testing, let's use these TFLInsurance endpoints:

| Method | Endpoint            | Purpose                       |
| ------ | ------------------- | ----------------------------- |
| POST   | `/api/auth/login`   | Authenticate a user           |
| GET    | `/api/policies`     | List accessible policies      |
| GET    | `/api/policies/101` | View a specific policy        |
| POST   | `/api/claims`       | Submit an insurance claim     |
| DELETE | `/api/policies/101` | Delete a policy, if permitted |

These are illustrative endpoints for our lab; actual routes and permissions depend on the API implementation.

The essential expectation is:

- No token: normally `401 Unauthorized`.
- Expired or invalid signature: normally `401 Unauthorized`.
- Valid token, insufficient permissions: normally `403 Forbidden`.
- Valid token with appropriate permissions: typically `200 OK`, provided the resource exists and other conditions are met.
- Resource not found: `404 Not Found`; some APIs deliberately return this instead of `403` to avoid revealing that a resource exists.

These are common conventions, not universal guarantees. Confirm the API's documented behavior.

## 7. JWT security test cases

Here is a practical test matrix for an Automation Test Engineer.

| Test case | Request condition                           | Expected result                                                                 |
| --------- | ------------------------------------------- | ------------------------------------------------------------------------------- |
| TC01      | Login with valid credentials                | `200` or documented success code; token issued                                  |
| TC02      | Login with invalid password                 | `401` or documented authentication error                                        |
| TC03      | Protected API without token                 | `401`                                                                           |
| TC04      | Protected API with malformed token          | `401`                                                                           |
| TC05      | Protected API with expired token            | `401`                                                                           |
| TC06      | Token signature tampered with               | `401`                                                                           |
| TC07      | Token signed with an untrusted key          | `401`                                                                           |
| TC08      | Token with wrong issuer or audience         | `401`, when those validations are configured                                    |
| TC09      | Customer attempts a manager-only operation  | `403`, assuming the identity is valid and the API uses this response convention |
| TC10      | Customer requests another customer's policy | Access denied; verify that no protected data is disclosed                       |
| TC11      | Valid token with valid permissions          | Expected success response                                                       |
| TC12      | Token passed in an unexpected location      | Reject it if the API only accepts tokens through the configured mechanism       |

Mentor's lesson: Do not test only whether a valid token works. Test whether every invalid token fails and whether a valid user is prevented from performing unauthorized actions.

## 8. HTTP status codes every tester should know

## 200

OK

Request succeeded

The server processed the request successfully.

## 201

Created

Resource created

Commonly returned after successfully creating a policy or claim.

## 400

Bad Request

Invalid request

The server cannot process the request due to invalid input or another client-side problem.

## 401

Unauthorized

Authentication failed or is missing

The request lacks acceptable authentication credentials.

## 403

Forbidden

Insufficient permission

The server understands the request but refuses to authorize the operation.

## 404

Not Found

Resource unavailable

The requested resource may not exist, or the API may conceal its existence.

## 9. Automating JWT tests using Node.js, Jest and Supertest

Once manual testing is clear, automate the same scenarios.

Install the packages in a Node.js testing project:

```
npm install --save-dev jest supertest
```

Assume the API has a test base URL and a login endpoint. The following is an illustrative Jest/Supertest example for a running test server:

```
const request = require("supertest");

const baseURL = process.env.API_BASE_URL;

describe("TFLInsurance JWT Security Tests", () => {
  test("Protected API rejects requests without a token", async () => {
    const response = await request(baseURL)
      .get("/api/policies");

    expect(response.status).toBe(401);
  });

  test("Protected API rejects an invalid token", async () => {
    const response = await request(baseURL)
      .get("/api/policies")
      .set("Authorization", "Bearer invalid.token.value");

    expect(response.status).toBe(401);
  });
});
```

For this example, configure `API_BASE_URL` to point to the running test instance, and adjust the route and expected status to match your API. Supertest can send requests to an HTTP server or an application instance; the example uses a URL.

A further test should obtain a genuine token through the login endpoint and verify that the protected request succeeds. Keep test credentials and secrets in environment variables or a secure test-secret store, not in source control.

## 10. Beyond JWT: what else should testers verify?

JWT is only one part of API security. Include these additional checks in your testing strategy:

- HTTPS: Ensure credentials and tokens are not transmitted over unencrypted HTTP in production.
- Broken object-level authorization (BOLA): Change a policy ID and try to access another customer's policy.
- Role escalation: Attempt manager-only operations with a customer token.
- Input validation: Send missing fields, invalid types, oversized input and unexpected values.
- Token exposure: Check that access tokens are not leaked in URLs, logs or error messages.
- Expiration and refresh: Verify expiration behavior and refresh-token rotation or revocation, if implemented.
- Rate limiting: Test whether repeated login attempts are controlled.
- Sensitive information: Ensure responses do not expose passwords, secret keys or unnecessary personal data.

## 11. Transflower mentor's final message

An Automation Test Engineer is not simply a person who sends requests and checks status codes.

A good tester thinks like a customer, a developer and a potential attacker.

When testing a secure REST API, ask:

1. Can an unauthorized user enter the system?
2. Can an authenticated user access someone else's data?
3. Can a customer perform an administrator's operation?
4. Can a modified or expired token bypass security?
5. Does the API fail safely without leaking confidential information?

Remember the principle:

> Authentication establishes identity. Authorization controls access. Automation verifies that the security rules cannot be bypassed.

At Transflower, we want students to progress from API consumers to API builders, and finally to engineers who can confidently verify the reliability and security of the systems they build.
