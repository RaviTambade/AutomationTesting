## 2. What is JWT?

JWT stands for JSON Web Token.

It is a compact string that carries claims about a user or client. A signed JWT lets the server verify that the token has not been modified and validate its claims.

A JWT has three parts:

1\. Header

Specifies the token type and signing algorithm, such as HS256.

2\. Payload

Contains claims such as user ID, role, issuer, audience, and expiration.

3\. Signature

Allows the server to verify the token's integrity and authenticity.

Combined format

header.payload.signature

Important: JWT payloads are normally encoded, not encrypted. Never put passwords or secret keys inside them.

```
JWT_SECRET=Transflower_Demo_JWT_Secret_Key_2026!
```

This is a placeholder for local learning, not a production secret. For production, generate a cryptographically random secret with sufficient entropy, keep it outside source control, and rotate it when necessary.

Load the configuration in Node.js:

```
require("dotenv").config();

const jwtSecret = process.env.JWT_SECRET;

if (!jwtSecret || Buffer.byteLength(jwtSecret, "utf8") < 32) {
    throw new Error(
        "JWT_SECRET must be at least 32 bytes"
    );
}
```

This example checks for a minimum of 32 bytes. Some libraries or application configurations may enforce different rules.

## 6. Understand token generation in Node.js

When login credentials are valid, the backend can create a token with `jsonwebtoken`.

```
const jwt = require("jsonwebtoken");

function generateToken(user) {
    return jwt.sign(
        {
            sub: String(user.id),
            role: user.role
        },
        process.env.JWT_SECRET,
        {
            algorithm: "HS256",
            expiresIn: "1h",
            issuer: "TFLInsurance",
            audience: "TFLInsuranceAPI"
        }
    );
}
```

For example, the payload might contain:

```
{
  "sub": "101",
  "role": "Agent"
}
```

The `sign()` function creates the JWT. The actual token also contains registered claims such as issuer, audience, and expiration based on the supplied options.

The example assumes that `user` has already been authenticated securely. Never generate a valid token merely because a client submits a user ID or role. Those values must come from trusted server-side logic.

## 7. Protect the API using JWT middleware

In Express, middleware runs before the controller. It can verify the token and stop an unauthorized request.

```
const jwt = require("jsonwebtoken");

function authenticateToken(req, res, next) {
    const authHeader = req.headers.authorization;

    if (!authHeader || !authHeader.startsWith("Bearer ")) {
        return res.status(401).json({
            message: "Access token required"
        });
    }

    const token = authHeader.split(" ")[1];

    try {
        const payload = jwt.verify(
            token,
            process.env.JWT_SECRET,
            {
                algorithms: ["HS256"],
                issuer: "TFLInsurance",
                audience: "TFLInsuranceAPI"
            }
        );

        req.user = payload;
        next();
    } catch (error) {
        return res.status(401).json({
            message: "Invalid or expired token"
        });
    }
}

module.exports = authenticateToken;
```

Use this middleware on the protected route:

```
const express = require("express");
const authenticateToken = require("./authenticateToken");

const app = express();

app.use(express.json());

app.get("/api/policies", authenticateToken, (req, res) => {
    res.status(200).json({
        message: "Policies retrieved successfully",
        userId: req.user.sub
    });
});

module.exports = app;
```

The route is illustrative. In a real application, it should call the policy service or repository to retrieve actual policy data.

## 8. Write JWT automation tests with Supertest

Now comes the Automation Test Engineer's responsibility: verify the API's security behavior.

Create `tests/jwt.test.js`:

```
const request = require("supertest");
const jwt = require("jsonwebtoken");
const app = require("../src/app");

require("dotenv").config();

describe("TFLInsurance JWT Authentication", function () {

    it("should reject requests without a token", async function () {
        const response = await request(app)
            .get("/api/policies");

        if (response.status !== 401) {
            throw new Error("Expected HTTP 401");
        }
    });

    it("should reject a malformed token", async function () {
        const response = await request(app)
            .get("/api/policies")
            .set("Authorization", "Bearer invalid.token.value");

        if (response.status !== 401) {
            throw new Error("Expected HTTP 401");
        }
    });

    it("should accept a valid token", async function () {
        const token = jwt.sign(
            { sub: "101", role: "Agent" },
            process.env.JWT_SECRET,
            {
                algorithm: "HS256",
                expiresIn: "5m",
                issuer: "TFLInsurance",
                audience: "TFLInsuranceAPI"
            }
        );

        const response = await request(app)
            .get("/api/policies")
            .set("Authorization", `Bearer ${token}`);

        if (response.status !== 200) {
            throw new Error("Expected HTTP 200");
        }
    });
});
```

Run the tests:

```
npm test
```

Testing note: The valid-token test creates a token using the configured signing key. This is useful for an isolated middleware test. For an end-to-end authentication test, obtain the token from the actual login endpoint instead. Keep test signing keys isolated from production secrets.

## 9. Essential JWT test scenarios

Use this checklist when planning your automation suite.

### JWT test plan

0/9 reviewed

Login with valid credentials

Expected: 200 and access token

Login with invalid password

Expected: Login rejected

Protected endpoint without token

Expected: 401 Unauthorized

Malformed token

Expected: 401 Unauthorized

Expired token

Expected: 401 Unauthorized

Token signed with wrong secret

Expected: 401 Unauthorized

Wrong issuer or audience

Expected: 401 Unauthorized

Valid token with sufficient permission

Expected: Expected success, e.g. 200

Valid token but insufficient role

Expected: 403 Forbidden, typically

The status codes above are typical expectations. Match them to your API's documented contract. Authentication failure generally returns `401`; a properly authenticated user who lacks permission generally receives `403`.

## 10. Authentication vs authorization

| Authentication                                        | Authorization                                   |
| ----------------------------------------------------- | ----------------------------------------------- |
| Who are you?                                          | What can you access?                            |
| Checks credentials or token validity                  | Checks roles and permissions                    |
| Invalid or missing credentials typically return `401` | Insufficient permissions typically return `403` |
| Example: Is this token valid?                         | Example: Can this agent approve a claim?        |

For TFLInsurance, an `Agent` might be allowed to view policies but not approve claims. A valid JWT does not automatically grant permission to perform every operation.

## Final mentor takeaway

A good Automation Test Engineer does not test only API functionality. The engineer also tests security boundaries.

- Node.js provides the runtime.
- Express handles API routes and middleware.
- jsonwebtoken signs and verifies tokens.
- Supertest sends HTTP requests.
- Mocha runs the test cases.
- Chai or Node.js assertions verify the outcomes.

Your practical learning sequence should be: first test login, then obtain a token, call a protected API, and finally test missing, malformed, expired, and unauthorized tokens.
